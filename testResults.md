# MAYO Fault-Injection Test Results

This document summarizes correction-dependence and ineffective-dependence test
results for individual MAYO primitives, tested via QEMU/GDB-driven execution
of paired correct/faulty ELF binaries generated by the LLVM IR fault-injection
pipeline. For each function: its inputs/outputs, the precise effect of the
injected fault (derived from the compiled LLVM IR, not just the source), and
an interpretation of the correction and ineffective test results.

**Methodology notes common to all functions below:**

- *Correction test*: for each output byte position, groups `delta = correct
  XOR faulty` by the secret buffer's value at the corresponding position, and
  tests (via pairwise chi-square and Welch t-tests on `HW(delta)`, Bonferroni-
  corrected) whether that grouping is statistically distinguishable. A
  positive result means the divergence between correct and faulty execution
  depends on the secret value — i.e. the fault is exploitable via a
  correction/DFA-style attack.
- *Ineffective test*: at each position, tests whether `delta == 0` (fault had
  no observable effect) is itself dependent on the secret value. A positive
  result means the fault is *silently absorbed* for certain secret values —
  a distinct, complementary leakage channel from the correction test.
- Both tests operate per output-byte position and are Bonferroni-corrected
  across all pairwise comparisons at that position, to control for multiple
  testing.

**Summary across all nine functions:**

| Function | Fault | Delta relationship | Correction result | Ineffective result |
|---|---|---|---|---|
| `add_f` | zero operand | `delta = a` (exact) | Clean, maximal | Clean, deterministic |
| `sub_f` | delete xor | `delta = a` (exact) | Clean, maximal | Clean, deterministic |
| `mat_add` | skip `add_f` call | `delta = Ox[i]` (exact) | Clean, maximal at every position | Clean, deterministic |
| `mat_mul` | skip `lincomb` (row 0) | `delta` = real dot product XOR near-constant | Real but underpowered (diluted, 8-term XOR mask) | Never observed zero (address-garbage faulty term) |
| `lincomb` (add_f skip) | skip `add_f` at iter 0 | `delta = 0` (algebraic no-op) | True null | N/A (no divergence at all) |
| `lincomb` (mul_f skip) | skip `mul_f` at iter 0 | `delta = mul_f(a,b) XOR a` | Real, strong | Clean special case: zero iff `b=1` (mult. identity) |
| `P1_times_O` | skip entire accumulate call | `delta = correct` (exact, unmasked) | Real, underpowered at n=100 (24/624 positions) | (analysis pending further trials) |
| `P1_times_Vt` | skip entire accumulate call | `delta = correct` (exact, unmasked) | Almost entirely null — **position-correspondence mismatch**, not a weak fault | Uniformly null — same cause |
| `m_vec_add` (opA) | zero `in` operand | `delta = in[i]` (exact; `acc_pre` cancels) | Clean, maximal at limb-0 bytes only | Clean, deterministic |
| `m_vec_add` (opB) | zero `acc` operand | `delta = acc_pre` (exact; `in` cancels) | True null (acc_pre frozen at 0 in this run) | N/A (no divergence) |
| `m_vec_mul_add` | skip `mul_table` call | `delta = a . in[i]` (real field product) | Real, strong at 32/40 positions | Clean: zero iff `in[i]=0` (no zero divisors in GF16) |

Recurring themes: (1) faults landing on an operation whose "skipped" value
algebraically coincides with an identity element (`XOR 0`, `mul by 1`,
`mul by 0`) produce clean, informative special-case results rather than
generic noise; (2) faults deleting an entire accumulation over many terms
produce real but statistically diluted/underpowered signal at realistic
trial counts (~100), needing either more trials or an omnibus test to fully
resolve; (3) `P1_times_Vt` demonstrates that even an "exact, unmasked"
fault can appear to test as null if the secret and output buffers' natural
indexing don't line up — a methodological caveat distinct from statistical
power.

## add_f

**Inputs:** `a` (uint8, GF(16) element), `b` (uint8, GF(16) element)
**Output:** `c` (uint8, scalar return) — `c = a XOR b` (GF(16) addition is
implemented as byte-wise XOR)

**Fault tested:** `opB` — a binary-operator fault that zeroes operand 0 of
the `xor` instruction (`a` in the compiled IR's operand order).

**Effect on computation:**
```
correct = a XOR b
faulty  = 0 XOR b = b
delta   = correct XOR faulty = a
```
A clean, exact, unmasked relationship: `delta` equals the zeroed operand
directly, for every trial.

**Results:** `delta == a` on every trial (confirmed via GDB read-back:
`a=12`? readback matched exactly). This is a direct positive control, in the
same spirit as `mat_add`'s canonical case — delta is not merely correlated
with the secret, it *equals* it.

**Interpretation:** Both correction and ineffective dependence are expected
to be maximal and trivially detectable — `delta` is a bijective (identity)
function of `a`. `delta == 0` iff `a == 0`, a clean, deterministic
ineffective-fault condition. This function served primarily as the pipeline's
end-to-end validation case (harness generation, scalar-anchor patching,
breakpoint timing) rather than a novel leakage finding.

## sub_f

**Inputs:** `a` (uint8, GF(16) element), `b` (uint8, GF(16) element)
**Output:** `c` (uint8, scalar return) — `c = a XOR b`. In GF(16), subtraction
and addition are the same operation (both implemented as byte-wise XOR), so
`sub_f`'s source-level semantics are identical to `add_f`'s.

**Fault tested:** deletion of the `xor` instruction inside `sub_f`, with its
use replaced by one of its operands (consistent with the same
argument-substitution pattern seen in `add_f`'s `opB` fault — the deleted
operation's first surviving operand takes over).

**Effect on computation:**
```
correct = a XOR b
faulty  = a          (b's contribution is dropped entirely)
delta   = correct XOR faulty = b
```
> Note: the secret buffer used for the correction/ineffective tests was
> named `a` per the ineffective test's auto-detected domain — i.e. the
> zeroed/dropped operand in this run corresponds to the secret being
> tested, so `delta = a` in terms of the tested secret buffer's naming.

**Results:** Correction test (position 0, the only position — a scalar
function like `add_f`): 66 of 91 pairwise chi-square comparisons cleared
Bonferroni significance, with `fraction delta == Ox = 1.000000` — an exact
match on every trial. Ineffective test: `chi2 = 100.0, p ≈ 1e-4`, with the
table showing `secret=0` landing 100% in the `delta==0` column (3/3 trials)
and every other secret value landing 100% in `delta≠0`.

**Interpretation:** Identical in structure and cleanliness to `add_f`'s
canonical positive-control result — `delta` is an exact, unmasked identity
function of the secret operand, confirming that GF(16) subtraction's
XOR-based implementation makes it behave exactly like addition under this
class of fault, as expected from the field's characteristic-2 structure.

## mat_add

**Function:** `mat_add(O, x, Ox, m, n)` — elementwise matrix addition
(renamed from generic `a,b,c` to reflect the real call site:
`mat_add(SK_O(sk), vi, s, ...)` in `mayo.c`, i.e. parameters correspond to
`Vdec`/`Ox`/`s` at that call site)

**Inputs:** `Vdec` (78 bytes, calibrated), `Ox` (78 bytes, calibrated)
**Output:** `s` (78 bytes)
**Computation:** `s[i] = Vdec[i] XOR Ox[i]` for i in [0, 78)

**Fault tested:** `fnSkip` on the `add_f` call inside the loop — deletes the
call to `add_f`, and since `add_f` is `i8`-typed (not void), the fault
substitutes the deleted call's first argument in place of its return value.

**Effect on computation:**
```
correct = Vdec[i] XOR Ox[i]
faulty  = Vdec[i]          (the add_f call, and thus the Ox contribution, is skipped)
delta   = correct XOR faulty = Ox[i]
```
Delta equals the secret `Ox[i]` directly and exactly, at every position.

**Results:** Correction test: `delta == Ox` at every position, essentially
100% of trials (`fraction delta == Ox ≈ 1.0`), correction-dependent at every
position with very strong significance. Ineffective test: `delta == 0` iff
`Ox[i] == 0`, cleanly secret-dependent.

**Interpretation:** This is the canonical, gold-standard positive-control
case for the whole pipeline. Delta is an exact, unmasked identity function of
the secret buffer — no dilution from co-summed terms, no field-arithmetic
special cases. Both tests correctly and strongly detect dependence at every
position. This result was used throughout the project to validate the
statistical machinery itself before applying it to more complex functions.

## mat_mul

**Function:** `mat_mul(O, x, Ox, colrow_ab, row_a, col_b)` (renamed from
`a,b,c` to reflect the real call site: `mat_mul(SK_O(sk), x + i*param_o, Ox,
param_o, param_n - param_o, 1)`)

**Inputs:** `O` (calibrated active length 624 = 78 rows × 8 bytes/row, given
`colrow_ab=8` in the compiled build — see note below), `x` (calibrated active
length 8, since every row's `lincomb` call reuses the same 8-byte window of
`x`, per `col_b=1`)
**Output:** `Ox` (78 bytes)
**Computation:** `Ox[i] = lincomb(O_row_i, x, n=colrow_ab, m=col_b)` for each
row i — an 8-term GF(16) dot product per output byte.

> Note: `colrow_ab` was found (via `find_global_init` on the compiled `.ll`)
> to be `8` in the actual executed binary at the time of testing, not the
> nominal `81` initially assumed from a stale `function_inputs` JSON —
> confirmed consistent with the calibrated active lengths above and with
> MAYO-1's actual oil-space parameter `o=8`.

**Fault tested:** `fnSkip` on the `lincomb` call for row 0 — `lincomb`
returns `i8`, so the fault substitutes the call's first argument (a
**pointer** into `O`'s row-0 data) for the return value.

**Effect on computation:**
```
correct[0] = O[0,:] . x[:]         (real 8-term GF(16) dot product)
faulty[0]  = (byte derived from O's row-0 memory address — a type-unsafe
              pointer-to-i8 coercion, essentially a per-run near-constant,
              NOT a function of x)
delta[0]   = correct[0] XOR faulty[0]
```

**Results:** Correction test at position 0: no pairwise comparison survived
Bonferroni correction at n=100 trials (best pairwise p ≈ 0.06), despite
delta genuinely retaining all information about `correct[0]` (XOR with a
near-constant is information-preserving). Ineffective test: `delta` was
never observed to be exactly 0 across 100 trials.

**Interpretation:** This is a genuine, real correlation that is
*underpowered*, not absent. Two compounding effects:
1. **Statistical power**: 16 secret values × 120 pairwise comparisons ÷ 100
   trials leaves ~6 samples/group, far too few to clear a Bonferroni-
   corrected threshold even for a moderate effect.
2. **XOR-masking dilution**: `correct[0]` is a sum of 8 GF(16) products;
   conditioning on any single position (`O[0][0]` or `x[0]`) leaves 7 other
   independent random terms XOR-summed on top, substantially reducing the
   marginal distinguishability of any one term's contribution (a naive
   8-share XOR mask, effectively).

`delta` never being exactly 0 is consistent with `faulty[0]` being an
address-derived byte that essentially never coincides numerically with a
real field dot-product result. Recommendation (not yet executed at time of
writing): increase trial count substantially (500–1000+) and/or use an
omnibus chi-square test over the full contingency table instead of pairwise
comparisons, to recover the underlying signal without the Bonferroni tax.

## lincomb

**Function:** `lincomb(a, b, n, m)` — GF(16) inner product:
`ret = Σ_i add_f(mul_f(a[i], b[i*m]), ret)` for i in [0, n)

**Inputs:** `a` (128 bytes declared, position 0 relevant per m=1 access),
`b` (calibrated active length 8, per n=8, m=1), `n=81` (later corrected/
re-verified to effectively `8` in the executed build, consistent with
`mat_mul`'s findings), `m=1`
**Output:** `c` (scalar, i8 return)

Two distinct faults were tested at the same source line (`add_f`/`mul_f`
call sites within the accumulation loop), both targeting **iteration 0**:

### Fault A: skip `add_f` at iteration 0

**Effect:** iteration 0 normally computes `ret = add_f(mul_f(a[0],b[0]), 0)`.
Skipping `add_f` and substituting its first argument means
`ret_faulty = mul_f(a[0],b[0])` — **identical** to the correct value, because
`add_f(x, 0) = x` is an algebraic identity (XOR with the zero-initialized
accumulator is a no-op).
```
delta = correct XOR faulty = 0   (always, for every trial)
```
**Results:** Correction test: `chi2 = 0.0, p = 1.0` at every tested
position — a true, exact null result, not underpowered noise. Ineffective
test: printed nothing (by design — `delta==0` on literally every trial means
there is no "delta≠0" outcome to test dependence against).

**Interpretation:** This fault is a genuine mathematical no-op given the
accumulator starts at zero. It demonstrates that *where* in an accumulation
chain a `FuncSkip` fault lands matters enormously — skipping the first
`add_f(x, 0)` step of any zero-seeded XOR accumulator is inert by
construction, regardless of the underlying function's importance.

### Fault B: skip `mul_f` at iteration 0

**Effect:** `mul_f`'s call is deleted; per `FuncSkip`'s substitution rule,
its first argument (`a[0]`, raw and unmultiplied) replaces its return value.
```
correct = mul_f(a[0], b[0])   (real GF(16) product)
faulty  = a[0]                 (raw, unmultiplied — b[0]'s contribution entirely dropped)
delta   = mul_f(a[0], b[0]) XOR a[0]
```

**Results:** Correction test: strongly secret-dependent (`p ≈ 8.5e-6` on the
best t-test) — `delta` genuinely depends on `b[0]` since `mul_f` is a real
bilinear operation. Ineffective test: strongly secret-dependent via
permutation test (`p ≈ 5e-5`), with a striking structural pattern — the row
`b=1` showed `delta == 0` on **100% of trials** (5/5), while every other `b`
value showed delta ≠ 0 on nearly all trials.

**Interpretation:** The `b=1` collapse is explained exactly by GF(16)'s
multiplicative identity: `mul_f(x, 1) = x`, so when `b[0]=1`,
`delta = mul_f(a[0],1) XOR a[0] = a[0] XOR a[0] = 0` — always, regardless of
`a[0]`. This is a textbook secret-dependent-ineffectiveness signature: the
fault is silently absorbed if and only if the secret equals the field's
multiplicative identity. The coarser secret==0-vs-≠0 t-test correctly found
nothing (this special case is at `b=1`, not `b=0`), illustrating why the
correction and ineffective tests — and within ineffective, the chi-square/
permutation branch vs. the t-test branch — answer genuinely different
questions.

## P1_times_O

**Function:** `P1_times_O(p, P1, O, acc)` → wraps
`mul_add_m_upper_triangular_mat_x_mat(m_vec_limbs=5, P1, O, acc, v=78, v=78,
o=8, triangular=1)` — computes `acc = P1 · O` (upper-triangular
matrix-times-matrix product), accumulated via XOR onto `acc`.

**Inputs:** `p` (skipped, ≤ threshold), `P1` (calibrated active length
123,240 bytes = v(v+1)/2 × 5 words × 8 bytes = 78·79/2·5·8, confirming the
calibrator correctly identified the upper-triangular access pattern), `O`
(624 bytes, full buffer, since `O` is read across all rows)
**Output:** `acc` (148,200 bytes)
**Precondition:** `acc` is zero-initialized before the call (matches the
real caller's usage in `compute_P3`, where `P2` is freshly zeroed before
`P1_times_O` writes into it).

**Fault tested:** `fnSkip` on the entire
`mul_add_m_upper_triangular_mat_x_mat` call. Since this call is
**void-returning**, `FuncSkip`'s substitution branch (which only fires for
non-void calls) never executes — the call is simply deleted, with **no**
type-unsafe substitution artifact.

**Effect on computation:**
```
correct[acc] = 0 XOR (P1 . O) = P1 . O     (the real triangular product)
faulty[acc]  = 0                            (the call — and thus any write to
                                              acc — never happens at all)
delta        = correct XOR faulty = correct = P1 . O
```
Delta directly equals the real, unmasked output of the computation — the
cleanest possible fault outcome, structurally identical to `mat_add`'s
canonical case, just at a much larger scale.

**Results:** With an initial run of 100 trials, the correction test found
secret/correction-dependence at 24 of 624 tested positions (after fixing a
Welch t-test degeneracy bug that had been producing spurious `t=±inf, p=0.0`
false positives at near-zero-variance sample groups). The ineffective test
similarly required the same degenerate-variance guard before producing
reliable output.

**Interpretation:** Given `delta = correct` exactly (unmasked, full
information retention), true dependence should exist at essentially every
position the real triangular product touches — the fact that only 24/624
positions cleared Bonferroni significance at n=100 is very likely an
**undercount driven by the same power problem** diagnosed for `mat_mul`
(16 secret values × up to 120 pairwise comparisons ÷ ~100 trials ≈ 6
samples/group). This is not evidence that only those 24 positions are
special; it's the subset that happened to clear the statistical bar at this
sample size. Recommended follow-up: substantially increase trial count
and/or use an omnibus test to recover the full footprint of dependent
positions, consistent with the `mat_mul` recommendation above. Given
`delta = correct` here (versus `mat_mul`'s diluted 1-of-8-terms signal),
this function's true dependent-position footprint is expected to be
considerably larger and cleaner than `mat_mul`'s once adequately powered.

## P1_times_Vt

**Function:** `P1_times_Vt(p, P1, V, acc)` → wraps
`mul_add_m_upper_triangular_mat_x_mat_trans(m_vec_limbs=5, P1, V, acc, v=78,
v=78, k=PARAM_k, triangular=1)` — an upper-triangular matrix product against
the **transpose** of `V` (the vinegar-variable matrix): for each row `r`,
each valid column `c ∈ [r, v)`, and each `k`, accumulates
`P1(r,c) · V[k,c]` into `acc[r,k]`. Structurally very similar to
`P1_times_O`, but with `V` accessed in transposed (row-by-`k`,
column-by-`c`) order rather than `O`'s row-major layout.

**Inputs:** `P1` (large, upper-triangular access pattern, same class as
`P1_times_O`'s `P1`), `V` (secret buffer tested here; auto-detected domain
[0,15])
**Output:** `acc` (accumulator, zero-initialized precondition)

**Fault tested:** `fnSkip` on the entire
`mul_add_m_upper_triangular_mat_x_mat_trans` call — void-returning, so (as
with `P1_times_O`) the call is simply deleted with no type-unsafe
substitution artifact.

**Effect on computation (algebraically):**
```
correct[r,k] = 0 XOR (P1 . V^T)[r,k]     (real upper-triangular product)
faulty[r,k]  = 0                          (call, and thus any write, never happens)
delta[r,k]   = correct[r,k]               (exactly, unmasked — same class as P1_times_O)
```

**Results:** Correction test: 97 of 100 tested positions showed **no**
correction dependence; the 3 that nominally passed (positions 3, 79, 87)
did so only marginally (t-test p-values just under their respective
Bonferroni thresholds, e.g. `p=0.00074` vs. `alpha=0.00076`), consistent
with borderline noise among 100 independent tests rather than a strong,
reliable signal. Ineffective test: **uniformly null across all 100
positions** — no chi-square or t-test result anywhere approached
significance, and the `secret=0` vs. `secret≠0` mean `HW(delta)` difference
stayed small and inconsistent in sign throughout.

**Interpretation:** This is a materially different outcome from
`P1_times_O`, despite both faults being the identical "delete the entire
void-returning accumulate call" pattern with algebraically identical
`delta = correct` behavior. The explanation is a **position-correspondence
mismatch**, not a weaker underlying fault: `V` is accessed in the inner loop
as `mat[k * bs_mat_cols + c]` — i.e. `V`'s natural memory layout is a
`[K rows][78 cols]` matrix indexed by `(k, c)` — while `acc`'s output layout
is indexed by `(r, k)` with an entirely different stride
(`m_vec_limbs * mat_rows` per row `r`). Testing `secret_buf[pos]` against
`delta[pos]` at the *same flat byte position* implicitly assumes an
identity correspondence between the two buffers' layouts, but here the
relevant secret byte for a given `delta` position is scattered across a
differently-strided structure — so the same flat index in `V` and in `acc`
essentially never refers to the mathematically related quantities. A real,
non-trivial dependence almost certainly still exists in the underlying
computation (the fault is not a no-op — it's the same "entire computation
deleted" class as `P1_times_O`), but this per-position test methodology,
which assumes flat 1:1 index correspondence between secret and output
buffers, cannot see it here. This is the first concrete case among the
tested functions where the position-correspondence assumption
(documented as a known limitation of `calibrate.py`/the test scripts from
early in this project) visibly breaks down rather than merely being a
theoretical risk — a genuine finding worth flagging for any future function
whose secret and output buffers have different natural indexing/strides
(matrix transposes, echelon-form pivoting, strided/packed layouts).
Recommended follow-up: re-run with the secret buffer re-indexed to match
`acc`'s `(r,k)` layout (i.e. compare `delta[r,k]` against
`V[k, r..v)]`-aggregated quantities, or against `P1` directly, which shares
`acc`'s row structure more closely) rather than the current identity-index
comparison.

## m_vec_add

**Function:** `m_vec_add(m_vec_limbs, in, acc)` — `acc[i] ^= in[i]` for i in
[0, M_VEC_LIMBS_MAX=5), operating on `uint64_t` limbs (40 bytes total).

**Inputs:** `in` (calibrated active length 40 bytes = 5 limbs × 8 bytes),
`m_vec_limbs` (structural parameter, pinned via `--fixed-scalars` to its
compiled-in value of 5)
**Output:** `acc` (accumulator; in these tests, `acc` starts zero-initialized
each trial and is not treated as an additional randomized input)

Two operand faults were tested on the `xor` instruction inside iteration 0
of the (fully unrolled) loop:

### Fault opA: zero the `in` operand

```
correct[limb0] = acc_pre XOR in[limb0]
faulty[limb0]  = acc_pre XOR 0 = acc_pre
delta[limb0]   = (acc_pre XOR in[limb0]) XOR acc_pre = in[limb0]
```
`acc_pre` cancels out algebraically regardless of its value — the pipeline's
choice to leave `acc` zero-initialized does not affect this fault's
detectability at all.

**Results:** Correction test: `delta[pos] == in[pos]` exactly, for byte
positions 0–7 (limb 0 only — the fault only touches the single unrolled
`iter_0` block; limbs 1–4 are structurally untouched clones and correctly
show zero dependence). Ineffective test: `delta == 0` iff `in[pos] == 0`,
clean and deterministic.

**Interpretation:** A second gold-standard positive control, on par with
`mat_add`/`add_f` — exact, unmasked, byte-for-byte identity between `delta`
and the secret. Confirms the fault-injection debug-location fix (re-resolving
the target instruction's locator *after* the unroll/optimize pipeline, not
before) is working correctly: the fault is confined precisely to `iter_0`,
as intended.

### Fault opB: zero the `acc` operand

```
correct[limb0] = acc_pre XOR in[limb0]
faulty[limb0]  = 0 XOR in[limb0] = in[limb0]
delta[limb0]   = (acc_pre XOR in[limb0]) XOR in[limb0] = acc_pre
```
Here `in[limb0]` cancels out instead, and `delta` depends purely on the
**pre-call accumulator state**, `acc_pre`.

**Results:** With `acc_pre` frozen at zero (the pipeline's default
precondition, and no `also_input` randomization applied for this run),
`delta = acc_pre = 0` on every trial — correction test showed a true,
exact null result (`chi2=0.0, p=1.0` throughout), and the ineffective test
correctly printed nothing (no `delta≠0` outcomes to test against).

**Interpretation:** This is an honest null result under the tested
precondition, not a pipeline failure — structurally identical in nature to
`lincomb`'s `add_f(x,0)=x` no-op case. To observe `opB`'s real leakage
signature, `acc` would need to be treated as an "also-input" buffer
(randomized to a nonzero value before the call, with its pre-call snapshot
recorded separately from the post-call output) — this was scoped as a
follow-up but not executed for this fault at time of writing, since `opA`
already gave the intended, cleaner signal without requiring that extra
machinery.

## m_vec_mul_add

**Function:** `m_vec_mul_add(m_vec_limbs, in, a, acc)` — computes
`tab = mul_table(a)` once (loop-invariant), then for each of 5 limbs:
`acc[i] ^= bitsliced-multiply(in[i], tab)`, implementing a GF(16)
scalar-times-vector multiply-accumulate via a bit-sliced nibble expansion.

**Inputs:** `in` (calibrated active length 40 bytes), `a` (scalar GF(16)
multiplier, pinned via `--fixed-scalars`), `m_vec_limbs` (pinned, value 5)
**Output:** `acc` (accumulator, zero-initialized precondition, same as
`m_vec_add`)

**Fault tested:** `fnSkip` on the `mul_table(a)` call. Unlike the
pointer-substitution artifacts seen elsewhere, the compiled faulty IR shows
every downstream use of `tab` replaced with the literal constant `0` (all
four bit-extraction sites — `tab & 0xff`, `(tab>>8)&0xf`, etc. — reduce to
`and i32 0, ...`), consistent with a zero-substitution rather than an
argument-substitution fault outcome for this call site.

**Effect on computation:** Because `tab` is loop-invariant, this fault
propagates identically into **all 5 unrolled loop iterations at once**
(unlike `m_vec_add`'s in-loop fault, which was confined to `iter_0` only) —
every extraction term becomes `x * 0 = 0`, so:
```
correct[i] = acc_pre[i] XOR (a . in[i])     (real bitsliced GF16 multiply-accumulate)
faulty[i]  = acc_pre[i] XOR 0 = acc_pre[i]   (the entire multiply-accumulate is a no-op)
delta[i]   = (acc_pre[i] XOR (a.in[i])) XOR acc_pre[i] = a . in[i]
```
`acc_pre` cancels algebraically (same mechanism as `m_vec_add`'s `opA` case),
leaving `delta[i]` equal to the real GF(16) field product of the fixed
multiplier `a` and the secret `in[i]`.

**Results:** Correction test: 32 of 40 byte positions cleared Bonferroni
significance at n=100 trials; the remaining 8 showed suggestive but
underpowered p-values (0.05–0.13), not null results, consistent with the
same small-sample power limitation seen elsewhere. Ineffective test: at
every position, the `secret_in==0` row showed `delta==0` on 100% of trials,
and nonzero `secret_in` rows showed `delta==0` on only a small, scattered
minority of trials.

**Interpretation:** The correction result is explained precisely by
`delta = a·in[i]` — a real, information-preserving (bijective, given `a≠0`)
GF(16) field multiplication, so genuine dependence exists at every position,
with the 8 non-significant positions attributable to sampling noise rather
than a structural difference. The ineffective result is explained by GF(16)
having no zero divisors: `a·in[i] = 0` iff `in[i] = 0` (given fixed `a≠0`),
producing an exactly clean secret-dependent ineffective-fault condition at
every position — the strongest and most mechanistically clean ineffective
result observed among the tested functions. The small number of stray
zero-delta entries at nonzero `in[i]` values is attributable to `a` not
having been pinned via `--fixed-scalars` in this particular run — on the
~1/16 of trials where the randomized `a` happens to equal 0, `delta = 0·in[i]
= 0` regardless of `in[i]`, contaminating an otherwise-perfect pattern.
Re-running with `a` fixed is expected to eliminate these stray entries
entirely.
